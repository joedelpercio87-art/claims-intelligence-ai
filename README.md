# Claims Intelligence AI

## Purpose

Claims Intelligence AI is a portfolio project for governed healthcare analytics using entirely synthetic claims data. It includes a deterministic analytics layer, local MCP adapter, local policy RAG, an OpenAI tool-calling investigation agent, and a local React executive interface.

## Synthetic data and intended use

All records generated by this project are fictional. Identifiers are synthetic; there are no names, exact dates of birth, addresses, contact details, government identifiers, medical record numbers, or real provider names/NPIs. Do not load real protected health information (PHI) into this repository or its future components.

This is not a clinical decision system and not an autonomous claims adjudication system. Data can support analysis of patterns, associations, and operational areas for investigation. It cannot establish fraud, abuse, medical necessity, improper clinical care, provider intent, or member fault.

## Architecture direction

```text
data/                 Local generated SQLite database (ignored by Git)
documents/            Reserved for future synthetic reference documents
src/database/         Schema, SQLite connection, deterministic generator, validation
src/tools/            Deterministic read-only analytics functions and verification
src/mcp/              Local stdio MCP server and protocol verification client
src/rag/              Fictional policy ingestion, embeddings, index, retrieval, and verification
src/context/          Reserved for future context engineering
src/agent/            OpenAI tool-calling claims investigation agent and verification
src/http/             Loopback-only API for dashboard metrics and investigations
app/                  React/Vite executive investigation interface
docs/                 Data and design notes
```

SQLite is the current structured persistence layer. Policy RAG is a separate unstructured evidence path. Both are exposed to the agent through MCP analytics and governed policy search. The local API and React interface present the agent's result and observable evidence trace; they do not implement separate claims logic.

## Responsible AI boundaries

- Use only the provided fictional, synthetic data in this project.
- Treat observed relationships as associations that need investigation, not proof of cause or wrongdoing.
- Keep humans responsible for review and decisions in any future workflow.
- Do not make or recommend clinical, coverage, payment, fraud, provider-intent, or member-fault determinations from these example records.

## Requirements and setup

Requires Node.js and npm. Install dependencies:

```sh
npm install
```

Generate or reset the reproducible database (seed `20260926`, 40,000 claim lines):

```sh
npm run db:generate
# or explicitly reset the local database first
npm run db:reset
```

The default database is `data/claims.sqlite`. Set `DATABASE_PATH` to change it. Generated SQLite files are excluded from Git.

Run TypeScript type checking and the validation report:

```sh
npm run typecheck
npm run validate
```

Validation reports row counts, month-level claim and denial metrics, denial categories, program comparisons, August provider concentrations, authorization-linked imaging outcomes, and foreign-key integrity.

## Deterministic analytics tools

`src/tools/analytics.ts` exports six read-only, parameterized SQLite analytics functions: `getClaimsPerformance`, `getDenialAnalysis`, `getProviderPerformance`, `getCostUtilization`, `getAuthorizationAnalysis`, and `getMemberPopulationImpact`. The functions use allow-listed filters and return aggregated observations; denial rates in the tools are claim-based. They do not produce causal or wrongdoing conclusions. Member results are grouped aggregates, not individual records. PMPM is not calculated because the synthetic data has no enrollment periods or member-month denominator.

Run `npm run analytics:verify` to exercise the tools and print monthly comparisons with observed facts separated from interpretation requiring additional evidence.

## Local MCP adapter

The local stdio Model Context Protocol (MCP) server exposes the six existing analytics functions to MCP-compatible applications. MCP provides a standardized interface through which an AI application can discover and invoke governed capabilities; it does not make the analytics or a model inherently smarter. The MCP handlers are thin adapters: they validate inputs, call the existing deterministic functions, and return structured results without implementing separate healthcare calculations.

Calling a TypeScript function directly is simpler for code already running in this project. MCP adds a protocol boundary that lets a separate local AI application discover tool names, descriptions, schemas, and invoke them over stdio without coupling that application to the analytics module. The tradeoff is an additional server/client process and protocol layer.

The server exposes exactly `getClaimsPerformance`, `getDenialAnalysis`, `getProviderPerformance`, `getCostUtilization`, `getAuthorizationAnalysis`, and `getMemberPopulationImpact`. Inputs use strict schemas and unknown fields are rejected; the adapter exposes no SQL tool. Database access remains read-only, and population results remain aggregated. The server requires no credentials or network access.

To run the stdio server for an MCP host, configure the host to launch `node` with `dist/mcp/server.js` from the project directory. Build first with `npm run build`; the convenience command `npm run mcp:server` builds and starts it. Stdio is reserved for MCP messages, so the process does not print normal logs to stdout.

Run `npm run mcp:verify` to launch the server as a child process, discover its tools, call each one through MCP, compare representative results with direct analytics calls, validate August outpatient imaging authorization statuses, and confirm arbitrary SQL input is rejected.

## Fictional policy corpus and local RAG

The six Markdown files under `documents/` form a fictional internal operations policy corpus. Every file carries the prominent disclaimer **FICTIONAL POLICY — CREATED FOR SYNTHETIC PORTFOLIO DEMONSTRATION ONLY**. These examples are not CMS, Medicare, Medicaid, HIPAA, payer, legal, clinical, or regulatory requirements and do not quote regulatory text. They contain generic procedures and do not describe any specific synthetic-data scenario.

RAG supplies relevant policy passages as unstructured policy evidence. It is separate from the structured operational evidence path:

```text
Structured:   Future Agent -> MCP -> deterministic analytics -> SQLite
Unstructured: Future Agent -> RAG retrieval -> fictional policy documents
```

MCP answers questions about observed claims metrics from SQLite. RAG retrieves internal policy text that may guide a human workflow. The local investigation agent can select from both paths, but keeps operational facts and fictional policy passages separately identified. Retrieved policy must not be represented as external regulatory fact.

Ingestion reads Markdown documents in filename order, identifies the policy title and H2/H3 section headings, and chunks within sections at about 1,400 characters with a small overlap. Each chunk retains filename, title, heading, and passage text. The configured embedding model is OpenAI `text-embedding-3-small`; the official OpenAI embeddings interface returns a vector for each supplied text. [OpenAI embedding documentation](https://developers.openai.com/api/docs/guides/embeddings)

The index is a local JSON vector file at `vector-indexes/policy-index.json`, excluded from Git. Retrieval embeds the question with the same model, computes cosine similarity locally, applies `RAG_MIN_SIMILARITY`, sorts by score, and returns up to `RAG_TOP_K` evidence passages with their provenance and scores. Defaults are top-K 4 and similarity threshold 0.35. The retrieval layer returns passages only; it does not synthesize an answer. Similarity is a ranking signal, not proof that a passage is authoritative or applicable.

Copy `.env.example` to the ignored `.env` file and set `OPENAI_API_KEY` locally. The key is read only from the process environment or ignored `.env`; it is not written to source, documentation, logs, or the index. Index building sends fictional policy chunks to the embeddings API, and each retrieval request sends its query text to that API for embedding. Keep both documents and queries free of PHI, real claim records, credentials, and unnecessary personal data. API use requires an OpenAI credential and may incur usage charges.

Commands:

```sh
npm run rag:index       # Rebuild embeddings and the local vector index
npm run rag:verify      # Run policy retrieval checks and the unrelated-query threshold check
npm run rag:retrieve -- "What should happen when an authorization is pending?"
```

Rebuild the index after editing any policy. Do not hand-edit generated vectors. Index metadata preserves fictional policy provenance so a future application can show the originating file and section. Retrieval can miss relevant text or rank a weak passage highly; users must inspect the quoted passage and its source before relying on it. No clinical, legal, coverage, payment, fraud, or abuse conclusion follows from retrieval alone.

## Claims investigation agent

`src/agent/claims-agent.ts` implements a command-line OpenAI Responses API tool-calling loop. At connection time, it discovers the existing MCP server's tools and allows only the six approved analytics names. Operational calls always travel through the local stdio MCP client; the agent does not import the analytics or database modules. `searchCompanyPolicies` is a separate governed capability that calls the RAG retriever and returns at most four matching passages above the configured threshold. The model chooses which evidence tools to call for each question.

The agent labels operational evidence as `OP-*` and policy evidence as `POL-*`, returns cited conclusions and evidence gaps, and records a public tool/context trace. The trace contains tool names, arguments, row counts, policy sources, sections, and similarity scores; it excludes hidden model reasoning. The prompt and verification suite enforce non-causal language, human review, aggregate-only population evidence, and the boundary that provider or authorization patterns do not establish wrongdoing or cause.

Run `npm run agent:verify` for seven synthetic investigation questions covering monthly claims performance, policy actions, service categories, authorization patterns, a provider accusation, AI decision authority, and an unrelated question. It calls the OpenAI Responses API and may incur API usage charges. Set `OPENAI_AGENT_MODEL` in the ignored `.env` to override the default `gpt-5.5`. The verification report records observable tool and evidence use, not chain-of-thought.

## Local executive web application

The React/TypeScript application is a presentation layer over the existing governed agent. Vite serves the interface at `http://127.0.0.1:5180` and proxies `/api` to the Express server at `http://127.0.0.1:5181`. Both services bind to loopback. The API exposes only a health check, an August dashboard metrics route, and a validated investigation route; it has no SQL or arbitrary tool endpoint.

The dashboard obtains July/August headline metrics by calling `getClaimsPerformance` through the existing stdio MCP server. An investigation POST invokes `ClaimsInvestigationAgent`, which continues to choose between the six MCP analytics tools and `searchCompanyPolicies`. The browser receives the final answer, evidence gaps, observable call parameters, a small aggregate-only result preview, and only the policy passages actually retrieved. OpenAI credentials remain in the local server process and are not included in Vite's browser bundle. The trace shows tool/context activity without chain-of-thought.

Start the local demo after installing dependencies and generating the database and policy index:

```sh
npm install
npm run db:generate       # if data/claims.sqlite does not exist
npm run rag:index         # if vector-indexes/policy-index.json does not exist
npm run dev
```

Open `http://127.0.0.1:5180`. The API health endpoint is `http://127.0.0.1:5181/api/health`. Stop both services with Ctrl+C. The API port can be changed with `API_PORT` and the UI dev port with `UI_PORT`; defaults are loopback ports 5181 and 5180. These defaults avoid conflict with common local development ports 5173 and 5175.

Run `npm run typecheck` for both server and browser TypeScript, and `npm run build` to compile the API and produce the Vite bundle under `dist/ui`. The portfolio verification commands remain `npm run validate`, `npm run analytics:verify`, `npm run mcp:verify`, `npm run rag:verify`, and `npm run agent:verify`.

### UI architecture and trust boundaries

- The browser has no SQLite connection, OpenAI SDK, embedding key, or direct analytics import. It can call only the local API routes.
- Dashboard numbers are read through the existing MCP server. Custom questions are validated server-side before being passed to the existing investigation agent.
- MCP remains the sole operational analytics path; RAG returns a limited set of fictional policy passages with filename, section, and similarity metadata. The policy corpus is never placed in the browser or model context wholesale.
- Responses show observed operational facts separately from interpretation and evidence gaps. Expandable evidence panels expose validated parameters, aggregate metric previews, and retrieved fictional passages. No individual member rows or chain-of-thought are presented.
- Synthetic data only, no PHI, read-only analytics, and human decision authority remain explicit. This demo does not make autonomous claims decisions.

For portfolio screenshots, use the August executive KPI row and a completed investigation such as the August performance question. Capture the answer cards alongside the expanded evidence path, then capture the separate fictional policy evidence panel for a policy question. Keep the synthetic-data and decision-support labels visible in screenshots; do not use real member or provider information.
